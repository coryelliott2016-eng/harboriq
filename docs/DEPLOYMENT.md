# HarborIQ — Deployment Guide

This is the operational counterpart to the root [`README.md`](../README.md):
how to actually run HarborIQ on a host, not how its code is organized. It
covers a **single-host Docker Compose deployment** — the honest scope for a
5-shop pilot, not a Kubernetes/multi-region design a pilot does not need yet.

## Prerequisites

- A host with Docker Engine + the Compose plugin (`docker compose`, not the
  standalone `docker-compose` v1 binary) installed.
- A domain name pointed at the host, if you want TLS (you should) — see
  "Reverse proxy and TLS" below.
- A Stripe account (test or live) if invoicing/payment collection is in use.
- An SMTP relay (Postmark, SES, Mailgun, or similar) if you want real email
  delivery instead of the console-log fallback (see README, "Auth
  hardening" → "Email transport").
- Optionally, a Sentry project if you want error reporting (see
  "Observability" below).

## Deploying with Docker Compose

The base `docker-compose.yml` is dev-friendly (publishes Postgres on the
host, builds images with a dev-shaped `VITE_API_URL` default). Apply
`docker-compose.prod.yml` on top of it as an overlay — do not use it alone:

```bash
cp .env.example .env   # then edit .env — see the table above
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.prod.yml exec app alembic upgrade head
```

What the prod overlay changes, and why, is documented inline in
`docker-compose.prod.yml` itself — in summary: `restart: unless-stopped`
everywhere, Postgres's `5432` is not published to the host at all (only the
`app` service can reach `db`, over the compose-internal network), real
resource limits, and secrets sourced from `.env` instead of hard-coded
defaults.

Both `Dockerfile` (backend) and `frontend/Dockerfile` are multi-stage
builds that run as a **non-root user** in their final stage and ship a
`HEALTHCHECK` — `docker compose ps` will show a container as `unhealthy` if
the backend's `/api/v1/healthz` (or the frontend's `/`) stops responding.

## Reverse proxy and TLS

Nothing in this repo terminates TLS or serves a public port directly —
that is a deliberate boundary, not an oversight. Put **Caddy** (simplest —
automatic Let's Encrypt certs from a two-line Caddyfile) or **nginx** (if
you already operate nginx elsewhere) in front of both containers, and have
it:

1. **Terminate TLS** on 443, redirect 80 → 443.
2. **Proxy `/` to the `frontend` container** (port `8080` inside the
   container — see `frontend/Dockerfile`; do not confuse this with
   whatever host port compose maps it to).
3. **Proxy `/api` to the `app` container** (port `8000`).
4. **Forward `X-Request-ID`** on the way in (and pass through the response
   header on the way back) — if the proxy already assigns request ids
   upstream of this app, HarborIQ's `RequestIDMiddleware`
   (`app/api/middleware.py`) reuses whatever the proxy sends instead of
   minting a second, disconnected id, so one id correlates a request across
   the whole hop chain. If the proxy does not already assign one, it should
   just pass the header through unmodified in both directions and let the
   app mint it.
5. Restrict `/metrics` and `/api/v1/readyz` to the scraper's/operator's
   network at this layer (see "Metrics" below). The app now also requires
   a bearer token for `/metrics` outside development (`METRICS_TOKEN`);
   network restriction remains the recommended second layer.

A minimal example Caddyfile (adapt hostnames/ports to your actual compose
port mappings):

```
harboriq.example.com {
    handle /api/* {
        reverse_proxy app:8000 {
            header_up X-Request-ID {header.X-Request-ID}
        }
    }
    handle {
        reverse_proxy frontend:8080
    }
}
```

## Logging

`app/core/logging.py` renders logs as human-readable console output in
`APP_ENV=development`, and as one **JSON object per line**
(`structlog.processors.JSONRenderer()`) everywhere else — that is the
format nearly every log shipper/aggregator (Loki, CloudWatch Logs,
Datadog, a plain `jq`-based grep pipeline) expects, versus ANSI-colored
key=value pairs meant for a human terminal. With Docker Compose, container
stdout/stderr already goes through the Docker log driver — `docker compose
logs -f app` shows the JSON lines as-is; pipe them through `jq` for
readability, or point the Docker daemon's log driver at a real aggregator.

Every log line emitted while handling a request carries a `request_id`
field (bound via `structlog.contextvars` by `RequestIDMiddleware`), which
also comes back to the client as the `X-Request-ID` response header — so a
support ticket that includes the response header value can be grepped
straight to its exact server-side log lines, without a separate distributed
tracing system.

## Metrics

`GET /metrics` exposes Prometheus text-format counters (`http_requests_total`)
and a latency histogram (`http_request_duration_seconds`), both labelled by
method/route-template/status — see `app/api/middleware.py`.

**Authentication (required outside development):** set `METRICS_TOKEN` to a
random secret (`openssl rand -hex 32`). The app rejects scrapes that do not
present `Authorization: Bearer <token>` with HTTP 401, and refuses to start
when `APP_ENV` is not `development` and the token is missing/short. In
development an empty token keeps open scrape for local Prometheus.

Prometheus scrape config (token auth is first-class — do not leave this
open and rely on obscurity):

```yaml
scrape_configs:
  - job_name: harboriq
    metrics_path: /metrics
    scheme: https
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/harboriq_metrics_token
    static_configs:
      - targets: ["api.harboriq.example:443"]
```

**Network restriction (defense in depth, still required):** even with a
bearer token, firewall `/metrics` to your scraper's network only. With the
Caddy example above, add a `handle /metrics` block restricted by `remote_ip`
to your monitoring host/VPN range; with a plain firewall, do not forward
port 8000/443 paths for `/metrics` to the public internet at all.

**What exists today vs. what does not, stated plainly:** the instrumentation
hooks above (structured logs, request-id correlation, the `/metrics`
endpoint) are real, working, and exercised by the test suite
(`tests/test_request_id.py`, `tests/test_metrics.py`). Standing up an actual
Prometheus server to scrape this endpoint, a Grafana dashboard, and a Loki
log-aggregation pipeline is a **deferred infrastructure decision** for
whoever hosts this — there is nowhere in this repo to deploy that stack to,
and pretending otherwise would be dishonest scaffolding. Wiring one up from
here is straightforward specifically because these hooks already emit the
right shapes: point a Prometheus `scrape_config` at `/metrics`, and a Loki
(or any JSON-aware) log pipeline at the container's stdout.

## Observability (Sentry)

Setting `SENTRY_DSN` turns on error and performance reporting
(`app/core/observability.py::init_sentry`) with zero other code changes;
leaving it empty (the default) means Sentry is never imported or
initialized at all — the same graceful-degrade pattern already used for
`STRIPE_API_KEY` and `SMTP_HOST` elsewhere in this codebase. There is
nothing else to configure.

## Health checks

- `GET /api/v1/healthz` — liveness. Returns `200` the moment the process is
  up; does not touch the database. This is what both Dockerfiles'
  `HEALTHCHECK` instructions call.
- `GET /api/v1/readyz` — readiness. Executes `SELECT 1` against the
  database and reports `{"status": "not_ready", ...}` (still HTTP 200,
  check the body) if that fails. Point a load balancer's readiness probe
  here if you ever run more than one `app` replica, so a replica that lost
  its DB connection stops receiving new traffic instead of erroring on
  every request.

## MFA / two-factor authentication (Phase 16)

Every user can enroll their own TOTP-based second factor from **Security**
in the app nav (`/settings/security`) — no admin action or backend
configuration is required to let users turn it on for themselves. What an
operator does need to do outside development is set a real
`MFA_ENCRYPTION_KEY` (see the environment variable table above) — the app
refuses to start in a non-development environment without one, the same
way it refuses to start with the placeholder `JWT_SECRET`. There is
deliberately no per-company or admin-forced "require MFA for all users"
policy toggle yet — enrollment is currently always self-service and always
optional; see the deferred items list.

## Database backups

`scripts/backup_db.sh` is a `pg_dump` wrapper meant for a host cron job —
not a managed-backup-service integration (that is explicitly out of scope;
see the script's own header comment). It dumps through the **service role**
(BYPASSRLS, so the backup captures every tenant, not whatever a single
RLS-scoped session could see), gzips the output, names it with a UTC
timestamp, and prunes dumps older than `BACKUP_RETENTION_DAYS` (default 14).

```bash
# One-off, using defaults (./backups, 14-day retention):
./scripts/backup_db.sh

# Configured for a real deployment:
BACKUP_DATABASE_URL="$SERVICE_DATABASE_URL" \
BACKUP_OUTPUT_DIR=/var/backups/harboriq \
BACKUP_RETENTION_DAYS=30 \
  ./scripts/backup_db.sh
```

Suggested cron entry (daily at 02:15 UTC):

```
15 2 * * * BACKUP_OUTPUT_DIR=/var/backups/harboriq /opt/harboriq/scripts/backup_db.sh >> /var/log/harboriq-backup.log 2>&1
```

**Copy the resulting `.sql.gz` files off the host** (`rclone`/`rsync` to S3
or another machine) on whatever schedule your recovery objectives require —
`scripts/backup_db.sh` alone only produces the artifact; getting a copy of
it somewhere other than the same disk as the database it backs up is what
`scripts/backup_db_s3.sh` (Phase 16) below adds, if you want it automated
rather than a manual `rclone`/`rsync` step.

Restore (destructive — restores into whatever `DATABASE_URL`/connection
string you point `psql` at):

```bash
gunzip -c backups/harboriq_20260101T021500Z.sql.gz | psql "$SERVICE_DATABASE_URL"
```

### Off-host backups to S3 (Phase 16)

`scripts/backup_db_s3.sh` wraps `scripts/backup_db.sh` unchanged and adds
exactly one thing: pushing the resulting dump to S3-compatible object
storage, if configured to. **It degrades gracefully with zero
configuration** — with no S3 env vars set, it runs the identical local-only
backup `backup_db.sh` always has and exits `0`; there is no reason a pilot
deployment without an AWS account cannot use this script as its cron
target from day one.

To activate the S3 push, an operator needs to:

1. **Create an S3 bucket** (or an S3-compatible bucket on Cloudflare R2,
   Backblaze B2, MinIO, etc.) dedicated to backups, ideally in a different
   account/region than the database host for real off-host durability.
2. **Create an IAM user or role** scoped to `s3:PutObject` (and ideally
   `s3:GetObject`/`s3:ListBucket` for restores) on just that bucket/prefix —
   not a broad admin credential.
3. **Install the AWS CLI** (`aws`) on the backup host if it is not already
   there (`apt install awscli`, or the AWS-provided installer).
4. **Set these environment variables** for the cron job (see
   `scripts/backup_db_s3.sh`'s own header comment for the full list and
   reasoning):

   | Variable | Required to activate S3 push? | Notes |
   |---|---|---|
   | `BACKUP_S3_BUCKET` | Yes — this is the on/off switch | Matches `app/core/config.py`'s `backup_s3_bucket` setting (documentation-only there; this script reads the env var directly). |
   | `BACKUP_S3_PREFIX` | No, defaults to `harboriq-backups` | Matches `backup_s3_prefix`'s default. |
   | `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | Yes, unless using an attached IAM instance/task role | Standard AWS CLI credential env vars — read by `aws` itself, not by this script. |
   | `AWS_REGION` | Usually yes | Standard AWS CLI env var. |
   | `BACKUP_S3_ENDPOINT_URL` | Only for a non-AWS S3-compatible provider | e.g. Cloudflare R2's account-specific endpoint. |

5. **Point cron at the new script instead of the old one:**

   ```
   15 2 * * * BACKUP_OUTPUT_DIR=/var/backups/harboriq \
     BACKUP_S3_BUCKET=my-company-harboriq-backups \
     AWS_REGION=us-east-1 \
     /opt/harboriq/scripts/backup_db_s3.sh >> /var/log/harboriq-backup.log 2>&1
   ```

**What this deliberately does not give you** (see the script's own header
comment for the full reasoning on each):

- **Point-in-time recovery (PITR).** A nightly `pg_dump` only ever restores
  to the moment it was taken — an RPO of "up to 24 hours," not seconds.
  True PITR needs continuous WAL archiving (pgBackRest, WAL-G, or a managed
  Postgres provider's built-in PITR feature), run continuously rather than
  cron'd. Adopt a managed-hosting provider's PITR feature when the business
  needs a tighter RPO than this script can offer — treat that as a hosting
  decision, not something to hand-roll here.
- **S3 lifecycle rules.** Transitioning old backups to cheaper storage
  classes or expiring them after N days is bucket configuration (console,
  Terraform, or `aws s3api put-bucket-lifecycle-configuration`), not
  something this script manages — it only ever `PUT`s objects.
- **Bucket creation, IAM policy setup, cross-region replication.** All
  one-time infrastructure setup, intentionally left to the operator/IaC
  tooling of choice rather than baked into a backup script that runs on
  every cron tick.

## CDN / WAF (Cloudflare) (Phase 16)

Nothing in this repo provisions a CDN or WAF — like the reverse-proxy/TLS
section above, that is a deliberate boundary: it is infrastructure that
sits in front of the reverse proxy documented above, configured once
through Cloudflare's own dashboard/API/Terraform provider, not through
anything in this codebase. This section documents **how to configure it
correctly for HarborIQ's specific traffic shape** if/when an operator
decides to put Cloudflare in front of the reverse proxy from "Reverse proxy
and TLS" above — it is not a requirement for a small pilot, and nothing
here has actually been provisioned or tested against a real Cloudflare
zone.

### DNS and proxy mode

- Point the domain's `A`/`AAAA` (or `CNAME`) record at the host running the
  reverse proxy (Caddy/nginx from the section above), with the record set
  to **Proxied** (orange cloud) rather than **DNS only** — only a proxied
  record gets Cloudflare's CDN caching, WAF, and DDoS protection at all.
- Set the zone's **SSL/TLS mode to Full (strict)**, not Flexible —
  Flexible would let traffic run unencrypted between Cloudflare and the
  origin, defeating the TLS termination already documented above. "Full
  (strict)" requires the origin's cert to be valid (Let's Encrypt via Caddy
  already satisfies this) and additionally validates its authenticity
  chain, which "Full" (non-strict) does not.

### Cache rules — static assets only, **never `/api/*`**

This is the one rule that matters most for correctness, not just
performance: **never cache anything under `/api/*`.** HarborIQ's API
responses are per-tenant, per-user, and often mutate server-side state
(rate limits, lockout counters, audit logs) as a side effect of being
called — caching a GET response at the edge risks serving one tenant's
data to another, or serving a stale `/api/v1/auth/me` after a role change.
Configure a Cloudflare **Cache Rule** (or Page Rule, on older Cloudflare
plans) scoped to:

- **Cache aggressively:** the frontend's static, content-hashed build
  assets — `/assets/*` (Vite's hashed JS/CSS chunks, filenames change on
  every build, so a long `Cache-Control: immutable` TTL is safe) and other
  clearly-static paths served by the `frontend` container (`/favicon.ico`,
  `/manifest.webmanifest`, the PWA service worker's precache manifest).
- **Bypass cache entirely:** everything under `/api/*` (backend requests),
  and the frontend's `index.html` itself (it must always be revalidated so
  a deployed frontend update is seen promptly, rather than an edge-cached
  copy of yesterday's `index.html` referencing build assets that no longer
  exist).
- Respect origin `Cache-Control` headers where the origin already sets them
  correctly, rather than overriding with a blanket edge TTL that could
  fight with them.

### WAF rules

- Turn on Cloudflare's **Managed Ruleset** (OWASP Core Ruleset equivalent)
  in at least "Log" mode initially, then "Block" once a burn-in period
  shows no false positives against real HarborIQ traffic (legitimate API
  payloads — job descriptions, customer notes, invoice line items — can
  occasionally trip generic SQLi/XSS heuristics; verify before blocking).
- Add a **rate-limiting rule** on `POST /api/v1/auth/login` and
  `POST /api/v1/auth/login/mfa` at the edge as a second layer in front of
  this app's own per-IP in-process (or Redis-backed, see README) rate
  limit — an edge-level limit stops abusive traffic before it consumes a
  backend connection at all, which the application-level limit cannot do.
- Do **not** rate-limit or challenge `/api/v1/webhooks/stripe` — Stripe's
  webhook senders come from Stripe's own published IP ranges and a CAPTCHA
  challenge or overly aggressive generic rate limit would break webhook
  delivery. If Cloudflare's bot-fight mode is enabled zone-wide, add an
  explicit bypass rule for that path.

### What this section deliberately does not cover

- Actually creating a Cloudflare account, zone, or API token — one-time
  account setup, not a per-deployment concern.
- Cloudflare Workers, Argo Smart Routing, Load Balancing, or other paid
  add-ons — none of these are needed for a single-origin pilot deployment;
  revisit if/when HarborIQ runs multiple origins across regions.
- Terraform/IaC for the above — the rules above are described as manual
  dashboard configuration since no Cloudflare account exists in this
  project to test an IaC module against; do not add a `cloudflare`
  Terraform provider block to this repo without first provisioning against
  a real zone to verify it.

## Running more than one app instance (Phase 16)

Phase 16 added Redis-backed rate limiting and Celery for background work
(see README, "Auth hardening") specifically so the `app` service is safe to
scale horizontally — this section is the readiness audit for actually doing
that, not a claim that compose already does it (the shipped
`docker-compose.prod.yml` still runs a single `app` replica; scaling it is
an operator decision, e.g. `docker compose ... up -d --scale app=3` behind
the reverse proxy's own load balancing, or a real orchestrator).

**Safe to run as N replicas today:**

- **Auth/session state** — JWTs are stateless, refresh-token rotation and
  session revocation live in Postgres (`user_sessions`), not in-process.
  Any replica can validate/refresh any session.
- **Rate limiting** — Redis-backed (see `app/core/rate_limit.py`), shared
  across replicas. Two replicas each seeing half of an attacker's requests
  still enforce the same global limit, because the counter lives in Redis,
  not in either replica's memory.
- **Idempotency / outbox dispatch / Celery tasks** — background work
  (`app/tasks/`) runs in Celery workers, not inside request-handling `app`
  processes; scaling `app` replicas does not change how many times a given
  Celery task executes, since that is governed by the worker pool and the
  task's own idempotency (see README).
- **MFA (Phase 16, this deploy)** — pre-auth tokens are stateless JWTs
  (`app/core/security.py`), TOTP/backup-code verification reads from
  Postgres — no in-process state.

**Deliberately still in-process, and why that is fine:**

- **`app/services/geocoding.py`'s outbound-request throttle.** This is a
  per-process token/rate limiter guarding calls *out* to the third-party
  geocoding provider, not a security or tenant-isolation control — its job
  is to keep any single `app` process from bursting past the provider's
  own rate limit, not to enforce a single global cap across all replicas.
  Running N replicas means the effective ceiling on outbound geocoding
  calls is N × (one process's throttle), which is the same trade-off
  singular-process rate limiters make in most codebases fronting a
  third-party API with its own generous-enough limit; move this to Redis
  too (mirroring `app/core/rate_limit.py`'s pattern) only if the geocoding
  provider's limit is ever actually hit in production with N > 1. Not
  moved proactively in this phase — see the deferred list.
- **In-memory request-scoped state** (request ID generation, per-request
  timing for structured logs) is correctly per-process by design; this is
  not shared state that needs coordinating, it is discarded at the end of
  every request regardless of replica count.

**Audited and confirmed to have no other per-instance state:** a
repository-wide search for other in-process caches/counters/singletons
under `app/` at Phase 16 turned up only the geocoding throttle above and
the (already-migrated-to-Redis) rate limiter — no other module keeps
state in a module-level variable, class attribute, or process-local cache
that would silently diverge across replicas.

**What actually changes to run N replicas for real:**

1. Scale the `app` service (`docker compose ... up -d --scale app=3`, or an
   orchestrator's replica count) behind the reverse proxy documented above
   — the proxy needs to load-balance across all replicas rather than a
   single fixed upstream.
2. Point the reverse proxy's readiness checks at `GET /api/v1/readyz` on
   *each* replica individually (see "Health checks" above) so a replica
   that lost its DB connection is taken out of rotation instead of
   continuing to receive traffic.
3. Run exactly one Celery worker pool (which can itself have multiple
   worker processes/concurrency) — Celery worker count is independent of
   `app` replica count and does not need to scale 1:1 with it.

## First-incident runbook (stub)

This is intentionally a stub, not a full incident-response plan — enough
to orient whoever is on call at 2 a.m. for a 5-shop pilot, not a 24-page SRE
doc a team of one does not need yet.

1. **Where are the logs?** `docker compose -f docker-compose.yml -f
   docker-compose.prod.yml logs -f app` (JSON lines outside development —
   see "Logging" above). If a user reports an error, ask for the
   `X-Request-ID` response header from their browser's network tab and
   grep for it directly: `... logs app | jq -c 'select(.request_id ==
   "…")'`.
2. **Is the app even up?** `docker compose ps` — look at the `HEALTHY` /
   `unhealthy` status column before doing anything else. Then `curl
   https://<host>/api/v1/healthz` and `/api/v1/readyz` from outside the
   host (through the reverse proxy) to confirm the whole path, not just the
   container.
3. **Did an email actually get stuck?** Outbound email (password resets,
   invites, invoice-send notifications) goes through the `outbox_events`
   table (see README, "Auth hardening" → "Email transport"). Rows that
   failed `MAX_DISPATCH_ATTEMPTS` (5) consecutive times move to
   `status = 'dead_letter'` instead of retrying forever. Check for them:
   ```sql
   SELECT id, event_type, attempts, last_error, created_at
   FROM outbox_events
   WHERE status = 'dead_letter'
   ORDER BY created_at DESC;
   ```
   A pile of dead letters with the same `last_error` almost always means
   SMTP credentials/connectivity broke — fix that, then manually
   re-queue by resetting `status`/`attempts` on the affected rows (there is
   no admin UI for this yet; it is a deliberate deferred item, see the
   README's consolidated deferred list).
4. **How do I roll back a bad deploy?** Nothing here is a rolling/canary
   deployment — a "deploy" is "pull a new image tag / check out a new
   commit and `docker compose up -d --build`". Rolling back is the same
   operation in reverse: redeploy the **previous known-good commit SHA**
   (`git checkout <sha>` server-side, or retag/pull the previous image if
   you push tagged images to a registry — this repo does not do that yet,
   see the deferred list) and `docker compose -f docker-compose.yml -f
   docker-compose.prod.yml up -d --build`. Because migrations are additive
   SQL files under `alembic/versions/` and this project has not yet needed
   a destructive migration, rolling the **code** back without also rolling
   the **schema** back is the normal case — do not run `alembic downgrade`
   reflexively; check whether the bad deploy actually shipped a migration
   first.

## What CI verifies that this deployment guide's author could not

This guide (and the code changes it documents) was written in a sandbox
with **no Docker daemon available** — every claim above about the
Dockerfiles/compose files building and running correctly is based on
careful manual review (plus `hadolint` static analysis of both
Dockerfiles), not an actual local `docker build`/`docker compose up`. The
`docker-build` job in `.github/workflows/ci.yml` is the first place either
image is actually built, on GitHub's own runners. Treat a green
`docker-build` run as the real confirmation that these files are
syntactically and structurally correct — not this document's prose.
